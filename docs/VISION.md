# Product Vision

CMMR is not a video editor product.

Media editing is the first serious vertical because it is useful, technically demanding, and exposes the architecture to real-world pressure. The long-term identity is broader: a local-first personal computing toolbox that lets a user make a phone do useful work without surrendering control to an account, subscription, cloud, or vendor.

## Core promise

**It should just work.**

That means:
- the obvious action should usually be the correct one,
- defaults should be safe and useful,
- advanced capability should not make basic workflows harder,
- errors should explain what the user can do next,
- the app should not require product knowledge just to complete ordinary tasks.

## User freedom

CMMR should prefer:
- local processing,
- local files,
- user-owned folders,
- replaceable providers,
- exportable project formats,
- optional cloud/services,
- no mandatory account,
- no ads,
- no dark patterns,
- no "premium diamond" UI sprayed through the app.

If a network service is added, it should be a service, not a hostage mechanism.

Examples:
- optional cloud render,
- optional backup/sync,
- optional hosted AI inference,
- optional relay/proxy infrastructure,
- optional hosted remote-control rendezvous.

Where practical, users should be able to self-host or use their own PC/server instead.

## Possible future verticals

Media is first. Other verticals may include:

- photo/video/audio editing,
- media/file organization,
- batch rename/compress/convert,
- backup/sync,
- local or remote AI tools,
- transcription/captions,
- remote PC control,
- phone <-> PC integration,
- local servers,
- game/Minecraft server helpers,
- tunneling/proxy helpers,
- local cloud/storage,
- download/import providers,
- automation and agent workflows.

These are possibilities, not a commitment to build everything.

## Scope control

Unlimited scope is fun and dangerous.

New verticals should pass three gates:
1. does the user actually want/use it,
2. can it reuse or cleanly extend existing boundaries,
3. can we build a useful vertical slice without destabilizing everything else.

Do not turn CMMR into an incoherent launcher full of half-built features.

## Monetization

The base product should remain useful without payment pressure.

Acceptable future revenue models are service-based:
- hosted rendering/compute,
- hosted AI inference,
- backup/storage,
- relay/proxy infrastructure,
- optional managed sync,
- donations.

Principle:
**sell scarce service resources, not artificial restrictions on local capability.**

A local capability should not be crippled merely to sell the hosted version of the same thing.

Paid services must not:
- block basic local workflows,
- nag continuously,
- inject ads,
- require an account before it is needed,
- hide ordinary controls behind premium badges.

The project should be economically sustainable without becoming hostile to its users.
